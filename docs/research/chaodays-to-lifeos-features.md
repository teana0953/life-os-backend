# chaodays → LifeOS 功能轉化底稿

> 目的:把 [chaodays 記錄功能研究](./chaodays-health-tracking.md) 轉化為 LifeOS 可實作的功能,作為後續 OpenSpec 提案的底稿。
> 本文只做「轉化與決策」,不重複描述 chaodays 本身 — 描述性研究看上面那份。
> 決策日期:2026-07-22(依實地重訪 dashboard 補充後定案)

## 一、範圍決策:只吸收「自我追蹤層」

chaodays 同時是兩個東西:①個人自我追蹤工具 ②營養師教練業務平台。**LifeOS 只吸收第①層。**

| 納入(自我追蹤) | 排除(教練業務,本文不處理) |
|---|---|
| 個人記錄、目標、達成率、趨勢、月曆 | 營養師↔學員關係、方案/訂單、預約課程、社群聊天室、教練人工「貼心提醒」 |

> 「貼心提醒」的個人化衛教留言,長期若要做,LifeOS 的版本應是 **AI 生成** 而非人工教練 — 但不在本輪範圍。

## 二、現況 gap(LifeOS 已有 vs chaodays)

| 能力 | LifeOS 現況 | 動作 |
|---|---|---|
| 飲食(份量) | 已有,雙軸 nutrient+portion 模型 | 沿用 |
| 喝水 | 已上線(backend #16 + frontend #43) | 沿用 |
| 排便 | 規劃中(次數+正常旗標+自由文字) | 既有規劃,不在本文 |
| 體重 | 已有 | 沿用/擴充(見功能 C) |

## 三、拆分:三個獨立 OpenSpec change,依序做

三項彼此相對獨立,且 LifeOS 用 dev-loop(一次一個 change)在推,故拆成三份 spec,依下列順序:

| 順序 | change | 為什麼這個順序 |
|---|---|---|
| **A** | 運動記錄 | 最小、最安全;完全複用已上線的 water/bowel「daily-log tracker」模板,先驗證流程。 |
| **B** | 生理期追蹤 | 自成一格(自己的月曆+週期預測),不依賴別人。 |
| **C** | 目標與成就 dashboard | 價值最高但依賴最多(要新增「目標/份量預算」領域概念,並聚合所有 tracker)。**放最後,才能一併涵蓋 A、B 新增的資料。** |

## 四、各功能轉化outline(供後續 openspec-propose 展開)

### 功能 A — 運動記錄

- **對應架構**:`src/contexts/health/`,複用 water tracker 的 daily-log 模式(port + `Drizzle...Repository` + use case + HTTP route + 前端 tab)。
- **資料模型(累計型,一天多筆)**:`{ date, activityId, durationMinutes, 備註? }`。與飲水同屬「累計」寫入語意,非快照。
- **預設運動庫**:含強度標註(如 慢跑 8km/hr)、有氧/無氧分類、可加常用/最愛。初版可用靜態 seed,不做使用者自訂庫。
- **⚠️ 關鍵耦合(chaodays 最巧妙處,設計時務必決定要不要做)**:運動會**即時增加當日飲食目標份數**(動越多能吃越多)。這是跨模組因果連結,是差異化所在,但會讓運動與飲食耦合。→ **設計時的岔路題:初版先做純記錄,還是一開始就做「運動→加食量」聯動?**
- **趨勢**:90 天運動量趨勢圖(可延後到功能 C 的 dashboard 一起做)。

### 功能 B — 生理期追蹤

- **對應架構**:`src/contexts/health/` 下新 tracker(或獨立 `menstrual` context,設計時定)。
- **資料模型**:`{ 起始日, 結束日? }` 每筆一個週期;衍生計算 **平均週期長度、平均經期天數、預測下次**。
- **設計動機(來自研究)**:生理期的目的不是獨立記錄,而是**解讀體重波動** — 避免經期水腫被誤判為復胖。→ 這決定了它未來要跟功能 C 的體重趨勢圖疊圖呈現。
- **UI**:小月曆(標記經期日)+ dashboard 顯示「最近一次生理期」。
- **開放題**:週期預測演算法初版取「近 N 次平均」即可,不需複雜模型。

### 功能 C — 目標與成就 dashboard

價值最高,是 chaodays 的核心體驗。是**建立在既有+新 tracker 資料上的呈現/聚合層**,含四塊:

1. **目標體重 + 達成率**:需新增「目標」領域概念(目標體重來自會員資料/個人設定)。首頁卡顯示「目標 / 今日 / 剩餘」三欄,及環形達成率。
2. **每日剩餘份量預算**:六大類設每日目標份量,吃一餐扣一餐,顯示「剩餘份量」(負數=超標)。這是 chaodays 依依不捨的核心畫面。目標份量依身高/體重/(+運動)算。
3. **記錄月曆 + 達標率成就**:月曆用圓點標「哪天有填飲食/體重」;三個環形指標(本月體重填寫率、飲食達標率、體重達成率)。
4. **體重體脂趨勢圖**:折線圖,可選區間(7/30/90 天);理想上與功能 B 生理期疊圖。

- **依賴**:讀取 A(運動,影響份量預算)、B(生理期,疊在趨勢圖)、既有飲食/體重/喝水。
- **新領域概念**:「目標/預算」— 建議獨立 value object,別散在各 tracker。
- **開放題**:份量目標的計算公式(身高體重→六大類份數)要跟誰對齊?先用固定公式還是可調?

## 五、跨模組設計原則(沿用研究結論)

1. **記錄粒度分層**:目標(依個人資料算)→ 容器(餐別/日期)→ 單筆記錄。
2. **累計 vs 快照要分清**:飲水/運動=累計(多筆相加);體重/體脂=快照(當日一筆)。兩種寫入語意。
3. **模組間耦合才是價值**:運動→加食量、生理期→解讀體重波動。優先設計這些連結,而非各自獨立的表。
4. **呈現「剩餘/距目標」而非累計值**更能驅動行為。

## 六、本輪明確延後 / 不做

- **份量查詢庫**(食物→份數家常單位換算):有價值但需維護資料庫,本輪不做。
- **份數制 vs 卡路里制** 的架構岔路:LifeOS 現況已走份量制,沿用,不重開此題。
- **AI 貼心提醒**(照片→估份數、個人化衛教):未來題,不在本輪。
- **教練業務層**(方案/訂單/預約/社群):範圍外。
