# 動態的「修改」列要說出改了什麼

## Why

`expense_updated` 的活動列只記金額的改前/改後。所以一次只動了描述、日期、付款人或**分攤比例**的修改,在時間軸上是一句沒有內容的「某人修改了這筆」,而且金額欄前後相同 —— 讀起來像什麼都沒發生。

**分攤比例的修改會改變餘額**,而那正是動態存在的理由:讓人看到「會改變我欠多少、而我不會被通知的事」。目前這一類完全看不出來,包括**被移出這筆支出**的那個人 —— 他收得到這一列(受眾是改前 ∪ 改後),但列上沒有任何內容告訴他發生了什麼。

## What Changes

- 活動列多三個欄位:`changed_fields`(封閉字彙)、`added_display_names`、`removed_display_names`。
- 只有 `expense_updated` 會寫,其餘型別一律 null,兩條 CHECK 擋住。

## 三個決定

### `shares` 一個字涵蓋「誰在裡面」與「各欠多少」

兩者都會動到別人的餘額。**同樣兩個人之間重新分配**沒有人加入也沒有人離開,總額還可以完全不變 —— 只看參與者集合的話,這種修改等於沒發生。

### 存名字,不存外鍵

跟這張表其他欄位同一個理由(design.md D2):列必須在它描述的支出被刪掉之後仍然讀得出來。而被移出的那個人正是**餘額被動了卻沒人通知**的那個讀者。

### 空陣列是一個答案,`null` 是另一個

更新端點是整份取代,所以客戶端重送一模一樣的值是**正常事件**。`[]` = 這次修改什麼都沒改;`null` = 這根本不是一列修改。把前者收斂成後者是說謊,而客戶端看不出來。

## 一個之前為了省一次查詢而留下的洞

「改前的分攤」原本**只有無群組的支出才讀**(因為只有無群組才要凍結受眾)。分攤的 diff 兩種都需要 —— 現在一律讀。多一次有索引的小查詢,換的是群組支出的分攤修改不再是一句空話。

## Impact

- `split_activity` 加三欄 + 兩條 CHECK(migration `0032`)。
- `update` 多讀 `currency` / `description` / `day`,以及所有支出的改前分攤。
- `SplitActivity` 型別、`activityToJson`。

## 明確不做

- **前端**(life-os#128 的 follow-up),那是分開的 change。
- **改前的完整分攤明細**(誰原本欠多少)—— 現在只說「分攤變了」加上誰進誰出。要逐人金額的話那是另一個決定,而且會讓每一列變大。
