- [x] 10.6 Amend `design.md`'s Risks section to record that `markMissedForUserDay` traded its old per-schedule failure isolation for D1's O(1) batching: a read failure now propagates to the caller's `step.do("mark-missed", ...)` for Workflows-level retry instead of being swallowed per schedule.
- [x] 10.7 A fleet whose subscription count makes `4 + 2 × subscriptions.length + 1` exceed even a completely fresh round's budget defers that slot identically on every wake, forever (every wake starts from the same budget) — a real, accepted limitation, documented in `design.md`'s Risks section and `specs/care-reminders/spec.md`. **Rejected fix, tried and reverted:** capping the subscription count the reserve accounts for (`MAX_RESERVED_SUBSCRIPTIONS`) so a large fleet's *estimate* stays affordable. This clamps the estimate without bounding what `sendClaimedSlot` actually sends, so a fleet past the cap gets claimed on a headroom check that reports "affordable" and then genuinely overruns the platform's real subrequest ceiling mid-dispatch. That overrun is not absorbed by D5/D6 the way it looks like it should be: the failure-recording write in `dispatchSlot`'s catch is itself one more subrequest against an already-exhausted budget, so it fails too, leaving the occurrence an abandoned claim that `ABANDONED_CLAIM_RETRY_MINUTES` retries — at the same remaining budget every time, since each retry is a fresh Workflows step wake — reproducing the identical overrun (and re-sending to every reachable subscription) every two minutes, forever, with no outcome ever recorded. Confirmed by construction (44 subscriptions, `MAX_RESERVED_SUBSCRIPTIONS = 20`, five simulated wakes: each sent 43 more pushes, occurrence stayed at `lastSendOutcome: null` throughout). Reverted to the uncapped reserve (`SLOT_DISPATCH_WRITES + 2 × subscriptions.length + FAILURE_RECORD_RESERVE`, no ceiling); a large-fleet slot instead defers on every wake, silently, which is strictly safer than a duplicate-send storm that never terminates. Added a brake test with `subscriptions.length >= 2` (the existing suite is entirely single-subscription and cannot distinguish the constant from the per-subscription product) and a regression test proving a fleet large enough to exceed a fresh round's budget still defers even given a full, fresh budget (no false "affordable" reading). **Superseded by section 11**: this "accepted limitation" was in fact a confirmed starvation bug (S >= ~21 permanently deferred, on every wake, forever, with no self-healing) — see 11.1.

## 11. Round 4: replace the all-or-nothing per-slot reserve with a fixed entry gate plus a per-send gate

- [x] 11.1 Confirmed (not merely suspected) that 10.7's "accepted limitation" is a real starvation bug: `SLOT_DISPATCH_WRITES + PER_SUBSCRIPTION_WORST_CASE × subscriptions.length + FAILURE_RECORD_RESERVE` gated the WHOLE slot on the WHOLE fleet's worst case before the claim, so `subscriptions.length >= 21` on a 50-request step made every slot for that user unaffordable on every wake, forever — every wake starts from the same fresh budget, and pruning a stale subscription only happens on an actual send, so a permanently deferred slot never self-heals. This repo has a documented incident of subscriptions accumulating past that count after a PWA reinstall, so the bug was reachable, not theoretical.
- [x] 11.2 In `dispatchDueRounds`, drop the `× subscriptions.length` (and the now-unused `reservedSubscriptions` snapshot) from the entry-gate check: `hasHeadroomFor(deps, SLOT_DISPATCH_WRITES + PER_SUBSCRIPTION_WORST_CASE + FAILURE_RECORD_RESERVE)`, a fixed cost of 7 independent of subscription count. This decides only whether the slot is worth claiming at all, not whether the whole fleet can be reached this wake.
- [x] 11.3 Add a `SLOT_TAIL_RESERVE` constant (`1` for the loop's own `recordAttempt` + `FAILURE_RECORD_RESERVE`'s fallback) and, in `sendClaimedSlot`'s per-subscription send loop, check `hasHeadroomFor(deps, PER_SUBSCRIPTION_WORST_CASE + SLOT_TAIL_RESERVE)` before EACH send; when it fails, stop sending to the remaining subscriptions (log `care-dispatch: stopped mid-slot after K/N sends, subrequest budget exhausted`) and fall through to the loop's normal `summarizeOutcome`/`recordAttempt` — never spending `SLOT_TAIL_RESERVE` itself, so that write is always affordable. A claimed slot therefore always ends with a recorded outcome: partial delivery to a subset of the fleet, never an unstarted slot and never one abandoned mid-dispatch.
- [x] 11.4 Replace `test/contexts/notifications/application/run-care-day.test.ts`'s two 10.7-era tests (which asserted the starvation as intended behavior — a 25-subscription fleet at a full fresh budget sending nothing) with: (a) a test that the entry gate no longer scales with subscription count (a 25-subscription slot is claimed on the same fixed budget a 1-subscription slot needs), (b) a test that a large fleet with a fresh, full-sized round budget is dispatched to in full rather than deferred, and (c) a test that a tight per-send budget stops the loop mid-slot, sends to only as many subscriptions as it can afford, and still records the slot's outcome (`lastSendOutcome`/`lastNotifiedAt` set, not left an abandoned claim). Mutation-verify: reverting the entry gate to the old `× subscriptions.length` form reddens (a); removing the per-send check, and separately shrinking `SLOT_TAIL_RESERVE`, each redden (c).
- [x] 11.5 Amend `design.md` D4 and its Risks section, and `specs/care-reminders/spec.md`'s subrequest-limit requirement, to describe the fixed entry gate plus per-send gate instead of the uncapped fleet-scaled reserve; keep the rejected-`MAX_RESERVED_SUBSCRIPTIONS`-cap history (it is still correctly rejected — a per-send gate solves the same problem the cap tried and failed to solve, without its overrun risk) but mark the uncapped-scaled-reserve design as superseded rather than current.
