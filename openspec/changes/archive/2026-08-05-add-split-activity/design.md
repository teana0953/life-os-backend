# 設計:分帳動態(split activity)

## 為什麼

分帳現在看不到「別人做了什麼」。支出列表能看到現有的支出,但:

- **刪除之後什麼都不剩。** `deleteExpense` 把列刪掉(shares cascade),使用者只會發現餘額突然變了,無從得知是誰刪了哪一筆。
- **修改只留下 `updatedAt`。** `updateExpense` 沒有記錄改了什麼,也沒有 `updatedByUserId`,所以連「誰改的」都不知道。

這兩件正是 activity 最有價值的部分——**會改變你欠多少、而你完全不會被通知的事**。「A 新增了一筆」在支出列表就看得到,「A 把那筆 $2000 刪了」則完全看不到。

參考 Splitwise:它的 Activity 是一條全域時間軸,包含新增、修改、刪除、結清、加入群組。

## 決策

### D1:事件表,不是從現有資料推導

推導式(union `splitExpense` / `splitSettlement` / `expenseGroupMember` 的建立時間)零 migration、零風險,但**看不到刪除與修改**——而那正是要解決的問題。推導式給的是「支出列表再排一次序」。

**選:新增 `split_activity` 表。**

### D2:活動列必須是**自足的快照**,不是外鍵

一筆「A 刪除了晚餐 $2000」的活動,如果只存 `expenseId`,那筆支出已經不存在,顯示時就只剩一個死 id。

**活動列要把顯示需要的東西全部存下來**:金額、幣別、描述、群組名稱、對象顯示名。這是刻意的反正規化,理由是**被記錄的東西本來就會消失**。

**還要存「誰看得到」。** 這是第一版漏掉的、而且會讓整個功能對它最該服務的情況失效:無群組支出的可見範圍是「參與者」,而參與者是從 `split_share` 算出來的——**支出一刪,shares 就 cascade 掉了**。於是「A 刪除了那筆 $2000」這條活動,事後**無法判斷該給誰看**。

所以**無群組**的活動必須在寫入當下把受眾一起存下來(`audience_user_ids` 欄位或子表)。

**但群組的活動不要凍結。** 群組永遠不會被刪除,所以它的成員名單是一個**活的、可靠的**來源;而產品其他地方(`listForUser`)本來就用活的成員資格決定「我看得到哪些群組支出」。凍結會讓時間軸和支出列表對「我是不是這個群組的人」給出兩種答案。

**所以規則是混合的,而兩邊各有理由:**

| 事件 | 受眾來源 | 為什麼 |
|---|---|---|
| 有群組 | **查詢時算**(該群組現任成員) | 群組不會消失;與 `listForUser` 一致 |
| 無群組 | **寫入時凍結** | 參與者存在 shares 裡,刪除時 cascade 掉,沒有別的來源 |

這也回答了「後來才加入的成員看不看得到之前的活動」:**群組的看得到**(跟他能看到之前的支出一致),**無群組的看不到**(他本來就不是參與者)。

代價要寫清楚:支出改名之後,舊活動仍顯示舊名。**這是對的**——活動是「當時發生了什麼」的記錄,不是現況的檢視。

### D3:原子性 —— 這是最容易靜默出錯的地方

活動寫入若與被記錄的異動不是同一個交易,兩種失敗都會發生:

- 異動成功、活動失敗 → **動態少一筆**,而使用者以為自己看到了全部。這比沒有這個功能更糟。
- 活動成功、異動失敗 → **動態顯示一件沒發生的事**。

這個 repo 這個 session 反覆踩到的最壞 bug 就是「告訴使用者做了、其實沒做」。

**選:活動的 insert 必須進入與異動同一個 `db.batch`。**

**八個裡只有三個現在有 batch**(expense `create`:106、expense `update`:165、group `create`:56)。**其餘五個都是單列寫入,全部要改成 batch**:expense `delete`(:171)、settlement `create`(:48)與 `delete`(:80)、group `archive`(:74)與 `addMember`(:83)。第一版說「只有 settlement create 是單列」——**錯了,是五個**。

**而 `db.batch` 本身擋不住刪除的幽靈活動。** expense delete 與 settlement delete 都是「先讀一次確認存在,再寫」,兩件事不在同一個交易裡。並發的雙重刪除下,DELETE 命中 0 列、呼叫端拿到 404,**而那句「A 刪除了 X」照樣被 commit**——正是 D3 宣稱要消滅的失敗。

**修法:讓 insert 條件化在同一個語句裡**(`INSERT ... SELECT ... WHERE EXISTS`),而不是靠先讀後寫。drizzle 0.45.2 有 `insert().select()`,結果是 `RunnableQuery`,可以和 delete 一起進 batch。

**但條件化只是把窗口變窄,並沒有關掉它——還要 `FOR UPDATE`。** neon-http 的 `db.batch` 是**一個 READ COMMITTED 交易**,而 READ COMMITTED 下**每個語句各自取自己的 snapshot**。所以沒有列鎖時,insert 的 snapshot 仍可能看得到來源列,而後面的 DELETE/UPDATE 在並發交易 commit 之後重新求值卻命中 0 列:活動被 commit、方法回 false、呼叫端拿到 404——正好還是這一節要消滅的那個失敗。

**所以三個條件化 insert 的來源 SELECT 都加 `for update of <alias>`**(expense delete `of e`、settlement delete `of s`、group archive `of g`)。insert 先取得列鎖,兩個交易就在這把鎖上被序列化:輸的那個等到贏的 commit 後重新檢查,來源列已消失(或 `archived_at` 已被設好),於是什麼都不寫,它自己的 DELETE/UPDATE 也命中 0 列。**恰好一個交易寫活動,而且是 DELETE/UPDATE 真的命中的那一個。**

無群組受眾用的 `array_agg` 不衝突:Postgres 只在**有聚合的那個查詢層**拒絕 `FOR UPDATE`,而該聚合位在純量子查詢裡,是自己一層(已用 PGlite 實測四個語句形狀皆合法)。

**這一段的正確性測試套件證明不了,要誠實寫下來。** PGlite 是單連線、沒有第二個 session(harness.ts 的隔離策略),所以無法讓兩個這種交易重疊;順序跑兩次刪除的測試,把鎖拿掉照樣綠,那種測試比沒有更糟。**套件只斷言「送出去的 SQL 真的帶著鎖、鎖在對的關聯上」**(`split-activity-write.test.ts` 的 “the emitted SQL takes a row lock”,三個路徑各自刪掉 `for update` 都會讓它變紅);鎖是否真的關掉競態,靠的是 Postgres 有文件的 READ COMMITTED 行為,不是這裡跑出來的證據。

**實作陷阱,務必寫進程式碼註解:條件化的 insert 必須排在 delete 之前。** 排在後面的話,同一個交易裡它看到列(以及 cascade 掉的 shares)已經不存在,於是**永遠靜默地什麼都不寫**,而「刪除不存在的東西不會留下活動」那類測試還是綠的。

**`archive` 需要的是另一個條件。** 群組永遠不會被刪除(只會封存,這正是 tasks 1.3 拿來論證 `groupId` 可以有外鍵的前提),所以「列還在不在」確實是一個到不了的狀態——但那從來不是這條路徑真正的條件。**`archived_at` 是單向的,而重複封存到得了**:`where id = ?` 一樣命中已封存的群組,UPDATE 成功、活動照寫,連按兩下封存鈕就讓時間軸說這個群組被封存了兩次。

**修法同一招**:UPDATE 與 insert 都帶 `archived_at is null`,insert 一樣排在 UPDATE 之前(排在後面的話,同一交易裡 `archived_at` 已經被設好,SELECT 命中不了,活動永遠靜默地不寫),來源 SELECT 一樣要 `for update of g`。第二次呼叫兩個語句都命中 0 列,`archive` 回 false,而 use case 不把它翻成 404——群組確實存在、也確實是封存狀態,404 會是第二個謊。

`archive` 少了鎖比刪除更糟一階:並發的**兩個「第一次」封存**會各自看到 `archived_at is null` 而**都寫進一筆**,卻只有一個 UPDATE 命中——時間軸會說這個群組被封存了兩次,正是這條要擋的狀態。

這代表活動的寫入落在 **adapter 層**,而不是 use case 層。分層上不漂亮(repository 知道了活動的存在),但替代方案是「use case 裡呼叫兩個 repository」,那正好就是非原子的那個。**activity 是 split context 內部的事,不是另一個 context**,所以耦合被侷限在 context 內。

**apply 時要為每一種異動各寫一條測試證明它們同生共死**——不是只證明活動有被寫入。

**這一條的第一版寫著「原子性沒有地方能真的測」——那句講過頭了。** `test/db/harness.ts` 說的是 `drizzle-orm/pglite` 沒有 `batch`,不是「無法原子」。**PGlite 是單連線**,所以 harness 補一個 `batch` shim(`BEGIN` → 依序執行語句 → `COMMIT`,任一失敗則 `ROLLBACK`)就能跑這些路徑,拿到**真的**原子性證據。

**選:替 harness 加那個 shim**,原子性用 PGlite 對真 Postgres 驗。shim 本身要有註解說明它模擬的是 neon-http 的 `db.batch`(非互動式、單趟),與正式環境不是同一個實作 —— 這是 harness 既有那三條界線的第四條。

假 `Db` 的結構性斷言(兩個語句在同一次 `batch` 呼叫裡)可以保留為第二層,但**不是主要證據**。

### D4:可見範圍 —— 第二個最容易寫錯的地方

活動應該給**受影響的人**看:

- 群組支出 / 群組結清 → 該群組的所有成員
- 無群組支出 → 該筆的參與者(payer + shares 的 user)
- 無群組結清 → 兩造
- 加入群組 → 該群組的成員

這是一段 SQL,而這個 session 已經有教訓:餘額查詢的述詞「存在」不等於「挑對了東西」。**驗收要用 PGlite 對真 Postgres 跑**(`test/db/`,PR #71 已經建好 harness),而且 fixture 要有多樣性(兩個群組、兩個不同的人扮演不同角色),否則「範圍存在卻不指定群組」這種突變會存活。

### D5:actor 與 viewer 分離

活動存的是 `actorUserId`,**不存「你」**。「你新增了一筆」與「A 新增了一筆」是同一列在不同讀者眼中的兩種呈現,由前端決定。後端不做這個判斷,否則同一列要為每個讀者存一份。

### D6:記哪些事件

八個寫入用例,全部記:

| 用例 | 事件 |
|---|---|
| create-expense | 新增支出 |
| update-expense | 修改支出(**要存改前/改後的金額**,否則「修改了」等於沒說;**金額沒變也照存**,讓讀者自己比對) |
| delete-expense | 刪除支出(快照) |
| create-settlement | 記錄還款(**要存方向**) |
| delete-settlement | 刪除還款(快照,**方向也要進快照**) |
| create-group | 建立群組 |
| add-group-member | 加入成員 |
| archive-group | 封存群組 |

`update-expense` 那條要注意:只寫「修改了」沒有價值,**要能看出改了什麼**。最小可用是金額的改前/改後;描述與參與者的變更先不做,寫進 follow-up。改前金額**每次都存**,不是「有變才存」——條件化會讓 `previous_amount != null` 被讀成「金額變了」,而那個讀法每次都錯。

還款那兩條同理:actor、counterpart、金額在「我付給他」與「他付給我」之下**完全一樣**,不存方向的話兩者是同一列;而 `settlement_deleted` 寫的時候被記錄的列正要消失,事後連再問一次都做不到。存成相對於 actor 的布林 `actor_is_payer`,而不是拆成兩種 type——同一列要同時服務兩造(D5),actor 照著讀、counterpart 反過來讀。兩條寫入路徑都已保證 actor 是兩造之一,所以「actor 付了嗎」問得出來;萬一不是,寫 NULL 讓 DB 的 CHECK 擋下,而不是存一個看起來合理的謊。

## 風險

- **`update-expense` 會整組換掉 shares**,所以它的受眾必須是**改前 ∪ 改後**的參與者聯集。只取改後的話,**被移出那筆支出的人永遠不會知道自己被移出了**——而那正好會改變他欠多少。
- **actor 不一定在受眾裡。** `created_by` 沒有出現在任何一條可見範圍規則中,所以照第一版寫法,操作者可能看不到自己做的事。受眾要包含 actor。
- **可見範圍目前只定義了八種事件裡的五種**(群組支出、無群組支出、群組結清、無群組結清、加入群組)。建立群組、封存群組、修改支出的受眾要補上。
- **可見範圍的 SQL 寫錯 = 洩漏別人的資料。** 這比餘額算錯嚴重:餘額錯是數字不對,可見範圍錯是把不該看到的內容給了別人。要用 PGlite 測,並且明確寫一條「非參與者看不到」的測試。
- **原子性測試很容易寫成假的**:證明「活動有被寫入」不等於證明「異動失敗時活動也不會留下」。要用突變驗證(把 batch 拆成兩次寫入,測試必須紅)。
- **反正規化的快照會與現況不一致**,這是刻意的(D2),但要在 API 與 UI 上講清楚,否則會被當成 bug。
- 這個 change **只做後端**;前端(分帳分頁內再開一個「動態」分頁)是下一個 change。
