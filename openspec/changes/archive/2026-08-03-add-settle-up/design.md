# settle up + 分帳整合進個人統計(sub-project 6,後端)— 設計

財務藍圖最後一塊。分帳(PR #65-#68)已上但**沒有還款概念**——餘額是全部歷史的淨額,現實中還了錢只能靠再開一筆反向支出,很難用。同時分帳與個人記帳完全平行,總覽看不到自己在分帳上真正花了多少。

## 使用者已裁定

- **還款記成獨立的紀錄**,不用反向支出充數。餘額 = 分帳淨額 − 已還額。
- **分帳只算「自己那份」進個人統計,不自動建交易**。不寫 `finance_transaction`,所以沒有雙寫入不同步的問題(這專案反覆出的那類)。
- **算進總覽與趨勢,不算進預算**。分帳沒有財務分類,塞進分類預算只能瞎猜;而且超支推播是寫入 `finance_transaction` 時觸發的,分帳不寫,硬要接就要多一條路徑與去重。

## 資料模型

### `split_settlement`

- `id` uuid pk
- `group_id` uuid **nullable** → `expense_group.id`(還款可以發生在群組內或一對一,與 `split_expense` 對稱)
- `from_user_id` / `to_user_id` uuid not null → `users.id`(**誰付錢給誰**——方向就是欠款被清掉的方向)
- `amount` integer not null(最小幣別單位)+ `currency` text not null
- `day` date not null(`YYYY-MM-DD`,與 `split_expense` 一致)
- `note` text nullable
- `created_by_user_id` uuid not null → `users.id`
- `created_at` / `updated_at` timestamptz
- CHECK `amount > 0`;**CHECK `from_user_id <> to_user_id`**(自己付給自己不是還款)
- index `(from_user_id)`、`(to_user_id)`、`(group_id)`

**不做**「一鍵結清」的自動拆解(把多筆欠款湊成最少轉帳次數)。那是 Splitwise 的 simplify debts,牽涉三方以上的債務重組,錯了會動到別人的帳。這一期只做「A 付了 X 給 B」這一件事。

## 餘額公式的改動

現有雙人淨額:

```
我對 X 的淨額(某幣別) = Σ(X 是分擔人 且 我是付款人).share − Σ(我是分擔人 且 X 是付款人).share
```

加上還款:

```
                       − Σ(X 付給我的還款).amount      -- X 還我錢,X 欠我的變少 → 淨額往下
                       + Σ(我付給 X 的還款).amount      -- 我還 X 錢,我欠 X 的變少 → 淨額往上
```

群組那段的主體不同,運算子因此相反:

```
成員 m 的群組淨額(某幣別) = Σ(m 是付款人的支出上,別人的 share)
                          − Σ(別人是付款人的支出上,m 的 share)
                          + Σ(m 付給別人的還款).amount   -- m 還錢,m 欠群組的變少 → 淨額往上
                          − Σ(別人付給 m 的還款).amount   -- m 收錢,m 的債權變少 → 淨額往下
```

**方向要想清楚,而且兩段 SQL 的符號約定不一樣**(proposal review 抓到;初版寫「群組餘額同理」是錯的):

| | 列的主體 | 正值代表 | 還款的加減 |
|---|---|---|---|
| 雙人 `balancesForUser` | **對方**(`counterpart_id` 是對方) | 對方欠我 | `對方 → 我` **減**;`我 → 對方` **加** |
| 群組 `balancesForGroup` | **成員自己**(付款人 `+`、分擔人 `−`) | 這位成員是債權人 | `成員 → 別人` **加**;`別人 → 成員` **減** |

兩者主體不同,所以同一句「from 就減」套上去會在群組那邊反向:群組裡的欠款人還完錢會顯示**欠更多**,而且不報錯。**兩段各自的純函式、各自的測試**,不要共用一個。

**還款的範圍與餘額的範圍要對齊**:雙人餘額的 CTE **沒有群組篩選**(它把有群組與無群組的支出一起算),所以加進去的還款腿也必須**涵蓋所有 `group_id`**;群組餘額只算 `group_id` 等於該群組的還款。實作者若照抄支出那條的 `WHERE se.group_id = ...` 到雙人那段,群組內的還款就永遠不會反映在好友畫面上。

**一個刻意留著的不對稱**:無群組的還款會減少雙方的「好友餘額」但不動群組餘額;帶 `group_id` 的還款兩邊都減。所以同一筆還款可能在一個畫面顯示已結清、另一個沒有。前端要引導使用者「清群組的債就帶 group_id」,後端不特判。

**同一幣別下所有成員 net 相加仍必為 0**——還款是成員之間的轉移,兩邊一加一減抵銷。但**這條不能拿來驗方向**(初版說它是「驗證方向沒寫反的最省力方式」,錯得很徹底):把加減號整組對調,零和照樣成立,測試照樣綠。零和只證明「有加也有減」,不證明加在誰身上。真正的方向驗證必須是**對指名成員斷言有號數值**:例如 B 欠 A 450,B 還 A 450 之後,斷言 A 的 net 是 0、B 的 net 是 0;B 只還 300 時斷言 A 是 +150、B 是 −150。

## 個人統計整合

新增一條**唯讀**的聚合:「我在某月的分帳自付額」,按幣別分列。

```
myShare(月, 幣別) = Σ split_share.amount
                    WHERE share.user_id = me
                      AND expense.day 落在該月
                      AND expense.currency = 幣別
```

- **付款人自己那份也算**——他確實吃了那餐、那筆錢確實是他的花費。這跟餘額計算刻意排除自己那份**不同**,因為問的是不同問題:餘額問「誰欠誰」,統計問「我花了多少」。這個差異要寫在程式碼註解裡,否則下一個人會以為其中一邊是 bug。
- **還款不算支出**。還錢是結清既有債務的資金移動,不是新的花費;算進去等於同一筆錢被計兩次。
- **不寫 `finance_transaction`**:總覽在讀取時把這條聚合併進去,分帳改了數字自動跟著改,沒有回頭補寫的問題。
- **預算不受影響**:`checkBudgetAlerts` 仍只在 `createTransaction` 觸發,分帳與還款都不觸發。

API 上**新增一條 endpoint**,不動 `/api/finance/summary` 的回應形狀——加欄位本身就是動形狀,初版那句「不改形狀,而是新增一個欄位(或一條 endpoint)」自相矛盾。理由不只是相容性:分開兩個數字,使用者才看得出「記帳支出」與「分帳自付額」的差別,也才回得去對帳。

## API

```
POST   /api/split/settlements                  # 記一筆還款
GET    /api/split/settlements?group_id=|?with= # 列出(與支出的篩選語意一致)
DELETE /api/split/settlements/:id              # 刪除(記錯了)
GET    /api/finance/split-spending?month=      # 我某月的分帳自付額,按幣別
```

**不做 PATCH**:還款只有金額/日期/備註三個欄位,記錯直接刪掉重記比部分更新單純,也少一條要重跑全部驗證的路徑(分帳那期的 PATCH 就是靠「重跑 create 的每一條規則」才守得住)。

## 授權

沿用分帳那套,一條都不放寬:

| 動作 | 誰可以 |
|---|---|
| 建立還款 | **呼叫者必須是 `from_user_id` 或 `to_user_id` 之一**;對方必須是好友或(有群組時)同群組成員;群組還款的雙方都必須是該群組成員 |
| 看還款 | 只有 `from_user_id`、`to_user_id`,或該群組成員 |
| 刪除還款 | `created_by_user_id` 或 `from_user_id`(付錢的人);其他人 **404** |

- **可見性失敗一律 404,不是 403**(403 等於承認 id 存在)。
- **封存的群組不收新還款**,但既有還款仍可刪除——與支出同一套理由:不讓錯誤永遠凍在裡面。
- 每條規則都要有「非參與者拿到 404」的反向測試。

## 併發與原子性

還款是**單列插入**,沒有 expense/shares 那種多列不變量,所以不需要 `db.batch`。但**刪除還款會改變餘額**,而餘額是即時聚合的,沒有快取要失效——這是刻意的選擇,寫在這裡免得日後有人加快取時忘了。

## 驗證與邊界(每條都要測)

- `amount <= 0` → 400;超過 2147483647 → 400(`integer` 欄位,不擋會變成 Postgres 22003 → 500)
- `from_user_id == to_user_id` → 400
- 幣別非三碼大寫 → 400;`day` 非 `YYYY-MM-DD` → 400
- 對方非好友且非同群組成員 → 400
- 呼叫者不是雙方之一 → 400(**不能幫別人記還款**,同分帳的反偽造規則)
- `group_id` 指向我不是成員的群組 → 404;群組還款的一方不是成員 → 400
- 非 uuid 的路徑參數 → 404,body 內非 uuid → 400(不擋會打到 Postgres uuid cast 變 500)
- 還款金額**允許超過目前欠款**(多還/預付是真實情況),不特別擋——餘額因此可以翻向另一邊,這是對的

## 明確接受的取捨

- **可以記一筆對自己有利的還款**。「呼叫者必須是 from 或 to 之一」擋住了幫兩個別人捏造還款,但擋不住「我付了你 100000」這種把對方餘額推向欠我的紀錄。這與分帳支出同一個處境(我也可以建一筆對自己有利的支出),兩者都靠**對方看得到、而且可以刪/爭議**來兜底,不是靠寫入時的檢查。這是有意識的取捨,不是漏掉;真要擋就需要雙方確認流程,不在本期範圍。

- **不做 simplify debts**(見上)。
- **不做還款提醒/通知**。
- **不做部分結清的 UI 捷徑**(「全額結清」按鈕由前端算金額後送一般還款,後端不特判)。
- **與最危險的兩段 SQL 同樣的測試缺口**:餘額聚合改了,而這個 repo 無法在 CI 執行 Drizzle SQL(假 `Db` 把 `where()` 參數丟掉,兩個 Vitest project 都沒有 Postgres 路徑)。緩解:**兩段各自的正負號抽成純函式並各自測**(對指名成員斷言有號數值,不是零和),兩段 CTE 的加減號照抄自它們並在 SQL 旁註解指回去。**但要誠實**:SQL 不會呼叫那兩支函式,測函式只證明函式對,不證明 CTE 跟它一致——CI 裡沒有任何東西能證明後者。零和只當附加的健全性檢查。**唯一能真的證明 SQL 方向沒寫反的是實機**:用兩個真帳號驗還款前後的餘額數字,雙人與群組各一次。
