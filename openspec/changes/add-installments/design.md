# 設計:記帳分期(issue #129)

## 需求(使用者定的)

- 記帳時可以選「分期」,自動在往後每個月產生明細。
- **12,000 分 12 期 = 每月 1,000**,分別落在 12 個月。**當月支出**就是照這樣算 —— 一次大額消費不會炸掉當月預算。(**趨勢與淨值不受影響**,它們讀手動快照;**預算進度只對 TWD 成立**,`spentSum` 寫死了幣別 —— 兩者見 D1。)
- **整組可以改**金額與期數。
- **提前付清**:剩下的合併成**今天一筆**,未來的列刪掉。
- **兩種產品都要涵蓋**:信用卡分期,以及房貸/車貸。

## D0:分期是一張「金額時程表」,**不是財務模型** —— 這條決定了整個範圍

**不存利率,不算攤還,不推算任何金額。**

房貸/車貸的月付金是本息攤還算出來的,牽涉利率、寬限期、指數型房貸的利率調整、提前還款違約金。**如果 app 算出 32,145 而銀行實際扣 32,148,帳本就是錯的** —— 而使用者會因此不再信任它。那不是記帳功能,是房貸試算產品。

**銀行才是權威,使用者從銀行抄數字過來。**

兩種產品共用同一個模型:

| | 信用卡分期 | 房貸/車貸 |
|---|---|---|
| 建立 | 選期數,系統平均分配(含除不盡的差額,見 D4) | **輸入銀行給的月付金**與期數 |
| 每月 | 一筆 | 一筆 |
| 提前 | **一次清償全部剩餘**(合併成今天一筆,D6) | 記一筆額外還款 + **改整組**成銀行重算後的新月付金(D5) |
| 利率 | 不存 | **不存** |

**部分提前還款 = 兩個既有動作的組合**,不是第三個功能:記一筆(真的付出去的錢)+ 改整組(銀行告訴你的新月付金)。

**這也消滅了「編輯一筆會不會連動後面」這個問題** —— 沒有任何重新攤分,所以編輯一筆就是編輯一筆交易。

**照銀行規則的兩件事實**(推薦時查證過,而且推翻了我自己先前的建議):
- **信用卡分期不提供部分提前還款** —— 只有照月繳或一次清償。所以「某個月多付一點」在信用卡的情境下不存在。
- **貸款可以部分提前**,而銀行讓你選「減少月付(期數不變)」或「縮短年限(月付不變)」,**台灣多數銀行的預設是前者**。我先前建議「提前付應該縮短期數」,那是貸款的**次要選項**,我把它當成通則推薦了。

**代價,要寫進 PR**:房貸調息或提前還款時使用者要手動更新整組。但他本來就得先知道新的月付金才能記帳,而那個數字只有銀行知道。

**如果之後要 app 幫忙試算(輸入本金/利率/期數產生攤還表),那是獨立的 issue**,不要塞進這裡 —— 而且要先確認還款方式(本息平均攤還 vs 本金平均攤還),否則算出來的表跟銀行對不起來。

## 決策

### D1:建立時就寫 N 筆真實交易,不是「一筆 + 重複規則」

真正 `SUM(finance_transaction.amount)` 的**只有兩處**:預算的 `spentSum`(`drizzle-finance-budget-repository.ts`)與 `getMonthlySummaryRaw`(`drizzle-finance-transaction-repository.ts`)。**第一版寫的「預算/月結/趨勢/淨值全都是」是錯的** —— **淨值與趨勢根本不讀這張表**,它們讀 `finance_networth_snapshot ⋈ finance_networth_account`(使用者手動輸入的月快照)。

結論不變(存成規則的話那兩處都要改,而且會改錯),但要用對的理由。

**而且這露出一個缺口:360 期的房貸永遠不會動到淨值。** 淨值只看快照,所以貸款餘額停在使用者上次自己輸入的數字。分期不會自動把它減下去。**這是刻意不做**(淨值本來就是手動快照制),但要寫進 PR,否則使用者會期待它自己更新。

寫成 N 筆普通交易,那些查詢**一行都不用動**,而且分期在明細裡看起來就跟手動記的一樣(使用者本來就期待在明細看到它)。

代價是「這 N 筆屬於同一組」需要另外表達,見 D2。

### D2:一張 `finance_installment_plan` + 交易上的可空 `plan_id`

- plan 存:期數、起始月、幣別、分類、備註,以及**建立時的輸入** —— 也就是重新產生未來期數所需的一切。
- 交易多一個 `plan_id`(可空)與 `installment_no`。

**兩種建立方式,要能分辨**(D0 的兩種產品):

| | 使用者輸入 | 系統做什麼 |
|---|---|---|
| 信用卡分期 | **總額** + 期數 | 平均分配,差額照 D4 分 |
| 房貸/車貸 | **每期金額** + 期數 | 直接照抄,不做任何除法 |

第二種**完全不能有除法** —— 一除就會跟銀行的數字對不起來,那正是 D0 要避免的。**這兩條路徑要有各自的測試**,而且要有一條證明「輸入每期金額時,產生的每一期都等於輸入值」(除法悄悄跑掉的話,這條會紅)。

**`plan_id` 必須可空且沒有 NOT NULL 的下游假設** —— 絕大多數交易不屬於任何分期。任何「假設交易一定有 plan」的程式碼都是錯的。

**刪除語意要想清楚**:plan 被刪時,它的交易要跟著刪(整組刪),所以 `ON DELETE CASCADE`。但**單筆交易被單獨刪掉時 plan 不受影響** —— 那會讓 plan 的「總額 = 各期之和」不再成立。**這是刻意接受的**:那些是真實交易,使用者有權單獨刪一筆,而 plan 只是「當初怎麼產生的」的記錄,不是必須恆等的帳。**要寫進註解**,否則下一個人會加一條讓它們對不上就報錯的檢查。

### D2b:所有計算只看**列**,永遠不看 plan 存的總額

D2 放棄了「總額 = 各期之和」,所以**任何用 plan 的總額去算錢的地方都會在使用者刪過一筆之後靜默算錯**。第一版就犯了這個:D5 的「剩餘 = 新總額 − 已發生之和」、D6 的信用卡清償都摸到了 plan 的總額。

**規則:改整組與清償的金額,一律從現存的交易列算出來。**

- 清償(信用卡)= **現存**的未發生期數之和。
- 改整組的剩餘 = 新總額 − **現存**的已發生期數之和。

語意上這也更對:使用者刪掉某一期,就是說「那期不會發生」,清償當然不該收它。

plan 存的總額**只是建立時的記錄**,不參與任何計算。**要寫進註解。**

### D3:月份推進 —— **要從起始日錨定,不能逐次遞增**

1/31 分 3 期 → 2/31 不存在。

**實測(review 在 PGlite 上跑過)**:
- `'2026-01-31'::date + interval '2 month'` → **2026-03-31** ✅(從起始日錨定)
- 逐次 `+ interval '1 month'` → 1/31 → 2/28 → **2026-03-28** ❌(一旦夾過就再也回不去,而且會一直漂移)

**選:每一期都從起始日算 `+ interval 'N month'`**,不是拿上一期再加一個月。

**這兩種寫法都滿足「2 月落在 2/28」** —— 所以 **fixture 必須斷言第三期是 3/31**,只檢查第二期的測試對這個 bug 是瞎的。第一版的 scenario 就是這樣寫的。

fixture 必須包含 **1/31 起算**與**閏年的 2/29**。

### D3b:期數上限 —— 房貸是 360 期,不是 24

第一版是照信用卡(≤24)設計的。使用者要的房貸是 **360 期**,而:

- 建立要寫 360 筆;一次清償要刪 N 筆 + 插 1 筆,tasks 要求同一個 `db.batch`。
- **PGlite harness 的 doc 明說它證明不了 neon-http 的語句數限制** —— 所以這會在本機全綠、在正式環境炸掉。

**上限查不到**:drizzle 的 `db.batch` → `sql.transaction([...])`,一個 HTTP POST;driver 1.1.0 的文件、原始碼與 Neon 官方文件**都沒有說**語句數或 body 上限。所以「先查出上限」這個做法行不通。

**要做的:讓語句數與期數無關。**
- 建立:**單一 multi-row INSERT**(`INSERT ... VALUES (...), (...), ...`),一句。
- 清償/整組刪除:**單一 `DELETE WHERE user_id = ? AND plan_id = ? AND day > ?`**,一句。**`user_id` 不可省** —— 少了它就是靠 `plan_id` 猜不出來當作安全性,而這裡刪的是別人的交易。**要有測試證明它挑對了列**(另一個使用者有同名的東西時不受影響)。
- 改整組:一句 DELETE + 一句 multi-row INSERT。

這樣 360 期跟 3 期的語句數一樣,上限是不是存在都不影響。**仍然設一個期數上限並回 400**(360 期已經是實務極限,不必支援 1000),但那是輸入驗證,不是為了繞開 batch 限制。

### D4:金額除不盡 —— 差額放哪一期(**只適用於信用卡那條路徑**)

**後端完全沒有小數位的概念**:`amount` 只是 `integer`,`SUPPORTED_CURRENCIES` 是一個沒有 metadata 的字串陣列,沒有 `finance_money.dart` 的對應物。所以**差額永遠是 1,與幣別無關**。

(前端有零小數幣別的表,但那是顯示層的事,後端不知道也不需要知道。)

**選:前面幾期各多一個最小單位,而不是全部丟到最後一期。** 3334 / 3333 / 3333。理由是最後一期特別大會讓人以為算錯,每期差一個最小單位不會。

**不變式:各期之和 = 總額,永遠。** 要有測試,而且 **fixture 必須包含除不盡的數** —— 這種測試最容易只用除得盡的數字,然後什麼都沒證明。

**第一版要求「fixture 要有零小數與兩位小數兩種幣別」,那是一個不可能失敗的守門** —— 沒有任何幣別相關的程式碼路徑可以突變。**不要寫它。**

### D4b:預算警示會為未來每個月觸發,而且把去重的列燒掉

**`createTransaction` 與 `updateTransaction` 都會呼叫 `checkBudgetAlerts`**(第一版只寫了 create),而它**用交易自己的月份**當 key。所以建一組 12 期會:

1. 為未來的月份推出通知;
2. 更糟:`finance_budget_alert` 對 (budget, month, threshold) 唯一,**未來那些月份的警示列現在就被寫掉**,等真的到那個月、真的超支時,**警示永遠不會再響**。

**但有一個條件,第一版漏了**:門檻判斷在 **`checkBudget`**(`check-budget-alerts.ts:59`),不是 `tryRecordAlert`(後者是無條件的 `onConflictDoNothing` 插入)—— 只有 `spent*100 >= amount*threshold` 才會往下走。而 `spent` 是**那個月的累計**,不是這一筆。所以每月 1,000 的分期在**那個月只有這一筆**時不會觸發,**35,000 的房貸月付會**。

**這讓測試的 fixture 變成關鍵**:金額必須大到那一期自己就跨過門檻,否則那條測試是空的 —— **一條保護 blocking 發現的假守門**。

第二點是靜默的、永久的,而且正是這個 repo 反覆出現的那類 bug。

**決定:警示只對「月份 ≤ 使用者的今天」的那些期數觸發。**

**這條規則有兩半,而且兩半都要有測試。** 被否決的做法(「帶 `plan_id` 的寫入一律不觸發」)**滿足所有只檢查『未來的沒被寫進去』的測試** —— 所以:
- **壓抑那半**:建立一組跨未來的分期後,未來月份的警示列沒有被寫進去。
- **觸發那半**:**清償那一筆(日期今天、金額最大)照常觸發當月警示。** 沒有這條,選這條規則的理由本身沒有被守住。
- 兩半各自突變驗證。

不是「分期寫入一律不觸發」—— 那會靜默壓掉**清償那一筆**的當月警示,而它日期是今天、在當月、**而且是這個功能能產生的最大一筆支出**。同樣的問題也發生在改整組重新產生的當月那一期。

用「月份 ≤ 今天」這條規則,四種情況一次解決:未來的期數不觸發、回溯建立的過去期數不觸發、當月的期數照常觸發、清償那一筆照常觸發。

**而且 `updateTransaction` 那扇門也要蓋到**:改一筆過去的 35,000 期數會重新觸發已結束月份的檢查。

### D5:改整組 —— 只改未來,而且要說清楚「未來」是什麼

已經過去的期數**不重寫**。它們發生過了。

改整組時重新產生的是**尚未發生的期數**,而剩餘總額 = 新總額 − 已發生期數之和。

**「今天那一期」算過去還是未來?** **算過去(已發生)** —— 它的日期已經到了,而清償那一筆也是插在今天。若把今天那期算成未來,清償會把它刪掉再用另一筆蓋回去,同一天出現兩次變動。所以 D3b 的 `day > ?` 用嚴格大於,`?` 是使用者的今天。

**「尚未發生」的界線是哪一天?** 用**使用者的今天**,不是 UTC 的今天。用 UTC 會讓 UTC+8 的使用者在當地凌晨改動時,把「今天那一期」誤判成未來(或反過來)。

**但這在財務 context 是第一次。** `users.timezone` 存在(預設 Asia/Taipei),而唯一的本地日期 helper 是 `notifications/domain/reminder-clock.ts` 的 `localParts()`,而它已經有**三個**呼叫者(`get-care-today`、`get-care-range`、`run-care-tick`)—— 不是第一版寫的一個。三個呼叫者都在 notifications 裡,所以「提升到 `shared/`」的成本比想像中低。**沒有任何財務用例讀過時區** —— 每一個財務寫入的 `day` 都是 client 傳來的。

**兩件要決定的事**:
- helper 提升到 `shared/`,還是跨 context import?
- **時鐘必須可注入**,否則「當地凌晨」那個 fixture 根本寫不出來(那是 UTC 與本地會給出不同答案的唯一時刻)。

### D5b:寬限期(房貸)—— 現在的模型表達不了

`指數型調息`由 D5 涵蓋(銀行重算後改整組)。但**寬限期不行**:前 N 期只繳息(例如 8,000),之後跳到 35,000,而且**這是建立當下就知道的**。一組 plan 只有一個「未來每期金額」。

**選:不支援排在未來,寬限期結束時使用者自己改整組。**

理由不是「比較簡單」,是另一條會壞掉:**允許 plan 從未來的月份開始會打壞 D6** —— 清償一個還沒開始的 plan 會刪光所有期數、然後把整筆插在**今天**,而今天在 plan 開始之前,那個月的預算與警示會被一筆不該存在的支出打到。D5 的「剩餘 = 新總額 − 已發生之和」在什麼都還沒發生時也沒有定義。

**代價**:寬限期結束時要手動改一次。使用者本來就得從銀行知道新的月付金,而那正是 D0 的立場。

### D6:提前付清 —— 只有「全部」,沒有「部分」

刪掉所有尚未發生的期數,在**今天**插入一筆。

**那一筆的金額,兩種產品不一樣 —— 這是第一版最嚴重的錯:**

| | 清償金額 |
|---|---|
| 信用卡 | 系統算:尚未發生的期數之和 |
| 貸款 | **使用者輸入**(從銀行抄) |

**因為貸款的「尚未發生的期數之和」裡含著未來的利息。** 真正的清償金額是剩餘本金加違約金,一定比那個和小。第一版一律用那個和,**那會是整個 change 裡唯一一處系統自己推算金額的地方,直接違反 D0**。

我寫了一整節說「不推算任何金額」,然後在清償那裡推算了一個。

**沒有「提前付 N 期」這個動作** —— 照銀行規則,信用卡分期只有一次清償;貸款的部分提前是「記一筆 + 改整組」(D0),而那兩個動作都已經存在。多做一個「付 N 期」會在兩種產品上都對不起銀行的實際行為。

**那一筆要不要掛 `plan_id`?** 要 —— 否則整組刪除時它會被留下來變孤兒。但它的 `installment_no` 是什麼?**做決定並寫理由**(給它最後一期的號碼?給 null?)。

**原子性**:刪 N 筆 + 插 1 筆必須在同一個 `db.batch` 裡。分帳那個 change 剛證明過,`db.batch` 是一個 READ COMMITTED 交易 —— 這裡沒有並發的先讀後寫,所以 batch 就夠,不需要 `for update`。

### D6b:金額不必等額

信用卡分期是系統平均分配,但**房貸/車貸的月付金由使用者輸入**,而且改整組之後新舊期數的金額會不同。所以:

- **不要假設一組分期的每一期金額相同。** 任何「拿第一期 × 期數」推出總額的程式碼都是錯的。
- plan 存的是**產生時的參數**,實際金額以交易列為準。

### D6c:回溯建立、最後一期之後、以及銀行事後改帳

**回溯建立**(貸款繳到一半才開始用這個 app):建立時會寫進約 80 筆**過去**的交易,而那些會**回頭觸發已經結束的月份的預算警示**(D4b 的同一個機制)。**要擋掉** —— 過去月份的期數不應該觸發任何警示。

**最後一期之後**:對一個已經走完的 plan 做「改整組」或「清償」會得到 0 期。**要明確定義**:回 400?還是靜默無事?**不要讓它產生一筆 0 元的交易或負數的剩餘。**

**銀行事後改帳**(例如追溯調整某一期):**金額上**模型天然支援 —— 那些是普通交易,直接改那一筆,不會重新攤還。

**但警示上不支援**:`updateTransaction` 也會呼叫 `checkBudgetAlerts`,所以改一筆過去的期數會**重新觸發那個已結束月份的檢查**。D4b 的「月份 ≤ 今天」規則要**同時蓋到 update**,不能只蓋 create。

### D6d:讀取 API 要讓前端做得出這個功能

第一版只加了 `plan_id` 與 `installment_no`。**那不夠**:

- 沒有**期數**,所以「第 3 期 / 共 12 期」渲染不出來。
- 沒有**建立模式**,而清償的 UI 必須知道它 —— 信用卡直接清償,貸款要提示使用者輸入金額(D6)。

**要有一個讀 plan 的方式**(端點或內嵌在交易上),至少回傳:期數、建立模式、起始月。**這次就做**,否則前端那個 change 第一天就卡住。

### D7:分期是支出,不是收入

`finance_transaction.type` 有收入/支出。**分期只對支出開放** —— 「分期收款」不是這個 issue 要的東西,而且會讓 D4 的差額分配、D6 的提前付清語意都要重想。**明確擋掉並回 400。**

## 風險

- **月底夾取沒測到 1/31**:整條路徑看起來都對,直到有人在 1/31 建立分期。
- **除不盡的差額只用除得盡的數字測**:不變式測試會通過而且什麼都沒證明。
- **「今天」用錯時區**:UTC+8 的使用者在當地凌晨改動時會少改或多改一期。這個 repo 的測試在 UTC 跑、開發機在 UTC+8,**兩邊都要驗**。
- **下游假設 `plan_id` 非空**:絕大多數交易沒有 plan,任何 join 或過濾寫錯都會讓一般交易消失。
- **建立 12 期就燒掉未來 12 個月的預算警示**(D4b),而且是永久的、靜默的。
- **360 期在本機全綠、在正式環境炸掉**(D3b),因為 PGlite 證明不了 neon-http 的語句數限制。
- **只檢查第二期的月份測試對「逐次遞增」的漂移是瞎的**(D3)。
- **總額小於期數**(例如總額 10 分 12 期):會產生 0 元的期數,而 `validateTransactionFields` 要求正整數 —— 建立會失敗,但失敗的訊息會很莫名。**要明確擋掉並給好的錯誤。**(這條在 round 1 提過,round 2 從所有文件裡消失了 —— 修文件時把它弄丟的。)
- **貸款那條路徑跑了除法**:使用者輸入的每期金額被「重新平均」一次,結果跟銀行差幾塊錢。看起來只差一點,但那正是 D0 說會讓人不再信任帳本的那種差。
- **不要偷偷長出財務計算。** D0 是這個 change 的範圍界線:一旦開始推算月付金,就要處理利率、寬限期、調息與違約金,而且算錯的代價是帳本與銀行對不起來。
- **不要假設等額**(D6b)。這是貸款進來之後最容易被既有直覺絆倒的地方。
- 這個 change **只做後端**;前端(記帳時選分期、明細上看得出是第幾期、一次清償的入口)是下一個。
