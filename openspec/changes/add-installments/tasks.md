# Tasks

**這個 change 的價值在於「帳本的數字等於銀行實際扣的錢」。** 任何自己推算出來的金額都是負債。

## 0. 盤點與前提

- [ ] 0.1 真正 `SUM(finance_transaction.amount)` 的**只有兩處**(review 逐一查過):預算的 `spentSum`、`getMonthlySummaryRaw`。**淨值與趨勢不讀這張表**(讀 `finance_networth_snapshot`)。第一版說「四五段」是錯的。**自己再確認一次。**
- [ ] 0.2 後端**沒有小數位的概念**(`amount` 只是 `integer`,`SUPPORTED_CURRENCIES` 沒有 metadata)。差額永遠是 1、與幣別無關。**不要寫幣別相關的 fixture 要求** —— 沒有可突變的路徑,那會是假守門。
- [ ] 0.3 `users.timezone` 存在,但**沒有任何財務用例讀過它**。helper 是 `notifications/domain/reminder-clock.ts` 的 `localParts()`,**已有三個呼叫者**(`get-care-today`、`get-care-range`、`run-care-tick`,第一版寫成一個)—— 都在 notifications 裡,所以提升到 `shared/` 比想像中便宜。**分期是財務的第一個**,見 4.2。
- [ ] 0.3b **「今天那一期」算已發生**(不是未來)。它的日期已經到了,而清償那筆也插在今天;算成未來的話清償會把它刪掉再蓋回去,同一天出現兩次變動。所以刪除述詞用嚴格大於。
- [ ] 0.4 **不要去查 neon-http 的語句數上限 —— 查不到。** drizzle 的 `db.batch` → `sql.transaction([...])`,一個 HTTP POST;driver 文件、原始碼與 Neon 官方文件都沒說。**改成讓語句數與期數無關**:建立用**單一 multi-row INSERT**,清除用**單一 `DELETE WHERE user_id = ? AND plan_id = ? AND day > ?`**。360 期與 3 期的語句數一樣。
  **`user_id` 不可省** —— 少了它就是拿「`plan_id` 猜不出來」當安全性。**要有測試證明它挑對了列**(另一個使用者的資料不受影響)。

## 0b. 兩個會靜默出事的東西 —— 先處理

- [ ] 0b.1 **預算警示會被未來的月份燒掉。** **`createTransaction` 與 `updateTransaction` 都會**呼叫 `checkBudgetAlerts`(第一版只寫了 create),它用**交易自己的月份**當 key;`finance_budget_alert` 對 (budget, month, threshold) 唯一。所以未來那些月份的警示列現在就被寫掉,**真的到那個月時永遠不會響**。
  **門檻判斷在 `checkBudget`(`check-budget-alerts.ts:59`),不是 `tryRecordAlert`**(後者是無條件的 `onConflictDoNothing`)—— 突變要下在前者。而 `spent` 是**那個月的累計**,所以每月 1,000 在那個月只有這一筆時不會觸發,**35,000 的房貸月付會**。
- [ ] 0b.1b **規則:警示只對「月份 ≤ 使用者的今天」的期數觸發**,而**不是**「分期一律不觸發」—— 後者會靜默壓掉**清償那一筆**的當月警示,而它是這個功能能產生的最大一筆支出。同一條規則一次解決四種情況:未來期數不觸發、回溯建立的過去期數不觸發、當月期數照常、清償那筆照常。
- [ ] 0b.1c **`updateTransaction` 那扇門也要蓋到** —— 改一筆過去的 35,000 期數會重新觸發已結束月份的檢查。
- [ ] 0b.1d **測試的 fixture 每期金額必須大到自己就跨過門檻**,否則那條測試是空的(一條保護 blocking 發現的假守門)。
- [ ] 0b.1e **規則有兩半,兩半都要測。** 被否決的做法(「帶 `plan_id` 的寫入一律不觸發」)**滿足所有只檢查『未來沒被寫進去』的測試**:
  - 壓抑那半:未來月份的警示列沒被寫進去。**突變:讓寫入走會觸發的路徑,必須紅。**
  - **觸發那半:清償那一筆(今天、金額最大)照常觸發當月警示。突變:改成「帶 plan_id 一律不觸發」,必須紅。**
  - 沒有第二條,選這條規則的理由本身沒有被守住。
- [ ] 0b.2 **期數上限。** 設一個明確上限並回 400(360 已是實務極限)。但那是輸入驗證,**不是**用來繞開 batch 限制 —— 繞開的方法是 0.4 的固定語句數。
- [ ] 0b.3 **總額小於期數**(總額 10 分 12 期)會產生 0 元的期數,而 `validateTransactionFields` 要求正整數 —— 會失敗但訊息莫名。**明確擋掉並給好的錯誤。**

## 1. 兩種建立方式 —— **每期金額**那條不可以有除法

(「每期金額 × 期數」同時服務**綁約訂閱**與**貸款**,不要把它寫死成貸款專用 —— 見 proposal 的框架。)

- [ ] 1.1 信用卡:**總額** + 期數 → 平均分配,差額照 D4。
- [ ] 1.2 貸款:**每期金額** + 期數 → **直接照抄**。
- [ ] 1.3 **寫一條測試證明 1.2 完全沒有除法**:輸入每期金額,產生的每一期都等於輸入值。**突變:讓它改走平均分配,必須紅。** 這條是 D0 的守門 —— 一除就跟銀行對不起來,而差幾塊錢看起來很像對的。
- [ ] 1.4 **不要假設等額**:改整組之後新舊期數金額會不同。任何「第一期 × 期數 = 總額」的推算都是錯的。

## 2. 差額分配(只適用 1.1)

- [ ] 2.1 前面幾期各多一個最小單位,不是全部丟到最後一期。
- [ ] 2.2 **不變式:各期之和 = 總額。**
- [ ] 2.3 **fixture 必須包含除不盡的數。** 但**不要**加幣別的要求 —— 後端沒有小數位概念,差額永遠是 1,**沒有可突變的幣別路徑**,那條會是假守門(第一版就是這樣寫的,而且寫在一條要求 fixture 多樣性以避免假守門的 task 裡)。
- [ ] 2.3b 順帶確認:預算的 `spentSum` **寫死 `currency = 'TWD'`**,所以規格說的「出現在預算進度裡」對非 TWD 的分期不成立。**要嘛修、要嘛把規格的說法收窄。**

## 3. 月份推進

- [ ] 3.1 **每一期都從起始日算 `+ interval 'N month'`**,不是拿上一期再加一個月。實測(review 在 PGlite 跑過):錨定得到 1/31 → 2/28 → **3/31**;逐次遞增得到 1/31 → 2/28 → **3/28**,而且會一直漂移下去。
- [ ] 3.2 **fixture 必須斷言第三期是 3/31。** 只檢查第二期的測試對「逐次遞增」的漂移**是瞎的** —— 兩種寫法的第二期都是 2/28。第一版的 scenario 就是這樣寫的。
- [ ] 3.3 fixture 必須包含 **1/31 起算**與**閏年 2/29**。

## 4. 改整組

- [ ] 4.1 只重寫**尚未發生**的期數,已經過去的不動。
- [ ] 4.2 **「尚未發生」用使用者的今天,不是 UTC 的今天。** 這在財務 context 是第一次(0.3)。要決定:`localParts()` 提升到 `shared/` 還是跨 context import?**而且時鐘必須可注入** —— 否則「當地凌晨」那個 fixture 寫不出來,而那是 UTC 與本地唯一會給出不同答案的時刻。測試在 `TZ=UTC` 與 UTC+8 都要跑。
- [ ] 4.3 剩餘總額 = 新總額 − **現存的**已發生期數之和(1.1 那條路徑);貸款那條是直接換掉未來期數的金額。
- [ ] 4.3b **所有金額計算只看現存的交易列,永遠不看 plan 存的總額。** D2 刻意放棄了「總額 = 各期之和」,所以任何用 plan 總額算錢的地方,在使用者刪過一筆之後就會靜默算錯。**寫一條測試:刪掉一筆未來的期數之後清償,金額是剩下那些的和,不是原本的。**

## 5. 一次清償

- [ ] 5.1 刪掉尚未發生的期數,今天插一筆。**金額兩種產品不一樣**:信用卡=**現存的**未發生期數之和;**貸款=使用者輸入**(從銀行抄)。
- [ ] 5.1b **貸款不可以用「尚未發生的期數之和」** —— 那個和裡含著未來的利息,真正的清償金額是剩餘本金加違約金。第一版一律用那個和,**那是整個 change 裡唯一一處系統推算金額的地方,直接違反 D0**。**寫一條測試釘住:給定金額的 plan 清償時用的是輸入值,不是剩餘之和。**
- [ ] 5.2 **沒有「提前付 N 期」** —— 照銀行規則,信用卡只有一次清償;貸款的部分提前是「記一筆 + 改整組」。
- [ ] 5.3 那一筆的 `plan_id` 要掛著(否則整組刪除時變孤兒);`installment_no` 給什麼?**做決定並寫理由。**
- [ ] 5.4 **原子性**:刪 N 筆 + 插 1 筆在同一個 `db.batch`。這裡沒有並發的先讀後寫,batch 就夠。**要有測試證明兩者同生共死**,而不是只證明「有插進去」。

## 6. 刪除語意

- [ ] 6.1 plan 刪除 → 交易 `ON DELETE CASCADE`。
- [ ] 6.2 **單筆交易被單獨刪掉時 plan 不受影響**,即使這讓「總額 = 各期之和」不再成立。**這是刻意的**,要寫進註解 —— 否則下一個人會加一條對不上就報錯的檢查。
- [ ] 6.3 `plan_id` 可空,**不可有任何下游假設它非空**。絕大多數交易沒有 plan;join 或過濾寫錯會讓一般交易消失。**寫一條測試:一般交易在所有既有查詢裡都還在。**

## 6b. 寬限期、回溯建立、走完之後

- [ ] 6b.1 **寬限期:不支援排在未來**,結束時使用者自己改整組。理由不是簡單 —— 允許 plan 從未來月份開始會**打壞 D6**:清償一個還沒開始的 plan 會把整筆插在今天,而今天在 plan 開始之前。
- [ ] 6b.2 **回溯建立**(繳到一半才開始用):會寫進約 80 筆過去的交易,而那些會**回頭觸發已經結束的月份的預算警示**。**要擋掉。**
- [ ] 6b.3 **走完之後、或被刪光之後**:對已結束的 plan(或使用者把期數一筆筆刪到剩 0 的 plan)做改整組或清償會得到 0 期。**明確定義**(回 400?靜默無事?),**不要產生 0 元交易或負數剩餘**。
- [ ] 6b.4 **銀行事後改帳**:**金額上**天然支援(普通交易,直接改那一筆,不重新攤還),**但警示上不支援** —— `updateTransaction` 也會觸發檢查,所以改一筆過去的期數會重新觸發那個已結束月份。0b.1b 的規則要同時蓋到 update。

## 7. 界線

- [ ] 7.1 分期**只對支出**開放,收入回 400。
- [ ] 7.2 **不存利率、不算攤還、不推算任何金額。** 這是 D0 的範圍界線。
- [ ] 7.3 若之後要做試算(本金/利率/期數 → 攤還表),那是獨立 issue,**不要塞進來**。
- [ ] 7.4 **淨值不會因為分期而變動** —— 淨值只讀手動的月快照,不讀交易。360 期的房貸不會自動把貸款餘額減下去。**這是刻意的,但要寫進 PR**,否則使用者會期待它自己更新。
- [ ] 7.5 **讀取 API 要讓前端做得出這個功能**,而不只是 `plan_id` / `installment_no`:
  - **期數**(否則「第 3 期 / 共 12 期」渲染不出來)
  - **建立模式**(清償 UI 必須知道要不要提示輸入金額)
  - 起始月
  **這次就做**,否則前端那個 change 第一天就卡住。
- [ ] 7.6 `spentSum` 寫死 `currency = 'TWD'`,所以**非 TWD 的分期不會出現在預算進度裡**。`checkBudgetAlerts` 也對非 TWD 早退。**要嘛修、要嘛在文件與 API 上說清楚。**
